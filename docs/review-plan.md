2. Цели ревью

1. Проверить производительность SQL-запросов на выборках размером в миллионы строк; время выполнения не должно превышать 5 секунд.
2. Проверить корректность агрегирования продаж, остатков и прогнозов при граничных данных и отсутствии записей.
3. Проверить читаемость запросов и возможность их поддержки другими разработчиками.

3. Критерии проверки (чек-лист)

3.1. Функциональная корректность

- [ ] Для эталонного набора данных результаты по продажам, остаткам и прогнозам совпадают с ожидаемыми зафиксированными значениями.
- [ ] Запросы корректно обрабатывают NULL, нулевые остатки, возвраты, отмененные продажи и пустые временные интервалы.
- [ ] Логика группировки, объединения и оконных функций возвращает одну строку для одного отчётного периода и одной аналитической группы.

3.2. Безопасность / Надежность

- [ ] Запросы используют параметризованные значения и не содержат динамического SQL с подстановкой пользовательского ввода.
- [ ] Отсутствуют неограниченные выборки; операторы LIMIT и фильтрация применяются там, где они нужны для объема отчета.
- [ ] Rollback и обработка ошибок не оставляют незавершенных транзакций при сбое построения отчета.

3.3. Производительность

- [ ] Каждый запроса на тестовом наборе миллиона строк выполняется не дольше 5 секунд.
- [ ] Для критичных запросов проверен план выполнения EXPLAIN (ANALYZE); отсутствуют последовательные сканирования крупных таблиц без приемлемой фильтрации.
- [ ] Индексы покрывают ключи фильтрации и объединения, а сортировки не создают неограниченных временных данных.

3.4. Читаемость и стиль

- [ ] SQL-файл отформатирован в соответствии с принятой командой стилем и правилами .editorconfig.
- [ ] Алиасы таблиц и имена колонок описывают бизнес-сущности и не являются необоснованно короткими.
- [ ] Сложные CTE и оконные функции снабжены краткими комментариями, объясняющими смысл расчета.
